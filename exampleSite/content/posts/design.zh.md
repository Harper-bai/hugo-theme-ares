标题说明你要解决什么，摘要交代读者为什么值得继续看，正文再把过程讲清楚。Ares 提供的是这些内容的容器；这篇指南把一篇文章需要的写法放在一起，方便直接开始。

<!--more-->

## 从一份完整文件开始

将下面的内容保存为 `content/posts/first-note.zh.md`，再替换标题、日期与正文。日期决定文章在首页和归档中的顺序，摘要分隔符决定首页展示到哪里。

````markdown {title="content/posts/first-note.zh.md" hl_lines=[2,4]}
---
title: 记录一次真正解决的问题
date: 2026-11-21T10:00:00+08:00
description: 从问题、尝试到结论，留下可复用的记录。
tags: [写作, 记录]
categories: [随笔]
---

这次遇到了什么问题？这篇文章能帮助谁？
用两三句话交代背景，让读者知道接下来会读到什么。

<!--more-->

## 问题从哪里开始

写下当时的目标、环境和观察到的现象。
保留关键条件，让后来的人能够理解你的判断。

## 尝试与证据

1. 描述第一次尝试。
2. 记录实际结果。
3. 解释下一步为什么这样选择。

> 把观察和判断分开，结论才有可以追溯的依据。

| 尝试 | 结果 |
| --- | --- |
| 复现问题 | 确认触发条件 |
| 调整方案 | 验证结果是否符合目标 |

## 留给下一次的结论

写下适用条件、尚未解决的问题，以及下一次的起点。

<details>
<summary>补充：复现时需要的条件</summary>

这里放环境信息或较长的背景说明。

</details>
````

代码块上方显示文件名。较长的示例会折叠，可以展开阅读，也可以直接复制完整内容。这里用高亮标出标题与描述，方便找到需要替换的信息。

## 让摘要完成自己的工作

摘要回答“这篇文章谈什么”，不必提前重复全部结论。`<!--more-->` 之前的部分显示在首页，之后的部分在文章页继续阅读。

很短的记录可以不写分隔符，首页会展示全文。文章较长时，建议明确写出摘要，避免首页被一篇文章占满。`description` 则用于页面描述，适合用一句话准确概括主题。

`draft: true` 适合尚未写完的文章。完成后移除它或改为 `false`，再用普通构建确认文章进入首页、归档与搜索。

## 给代码明确的文件名

围栏代码块可以指定语言和文件名。例如使用 `go` 语言并添加 `{title="hello.go"}`，读者就能知道代码属于哪个文件：

```go {title="hello.go"}
package main

import "fmt"

func main() {
    fmt.Println("Hello, Ares!")
}
```

需要强调特定行时添加 `hl_lines=[2,4]`；不需要行号时添加 `linenos=false`。复制按钮只复制代码正文，不带行号。说明代码时，先讲清它解决的问题，再让读者看实现。

## 把补充信息放在合适的位置

引用适合标出原文或值得停下来的句子。表格适合比较同一组维度。操作步骤用有序列表。较长的环境说明或旁支讨论，可以放进原生 HTML 折叠区块。

<details>
<summary>折叠内容里适合放什么？</summary>

放不影响主线的补充信息，例如完整环境、额外示例或进一步阅读。展开后，标题与正文之间会留出间距。

理解结论所必需的条件应直接写在正文里，让读者在第一次阅读时就能看到。

</details>

使用这些 HTML 区块时，需要保留配置中的 `markup.goldmark.renderer.unsafe = true`。示例配置已经开启。

## 发布前，站在读者的位置读一遍

检查标题是否具体，摘要是否准确，链接是否能打开。复制一次示例代码，切换一次明暗主题，再用手机宽度读完开头和结尾。

文章内容确定后，为它选择一个稳定的分类，再补上少量准确的标签。下一篇[归档整理指南]({{< relref "archive.zh.md" >}})会说明怎样让这些入口长期有用。
